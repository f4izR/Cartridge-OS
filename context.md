# Context for Agents

Read this before working on Cartridge OS. Also read `README.md` (product vision/roadmap), `progress.md` (what's done), and `production-readiness.md` (what's left for shipping).

## What this is

A Windows game launcher: console-dashboard style, fullscreen, controller-first, detects games from every major PC launcher (Steam, Epic, GOG, etc.) plus manual additions. No accounts, fully offline.

These four are **meaningfully less trustworthy** than Steam/Epic/Riot: there's no documented manifest to key off, so both the exact `Publisher` string per launcher and the exe-guessing heuristic are unverified assumptions. Plus Riot via `Scanning/RiotManifest.cs` + `RiotScanner.cs` (real documented `RiotClientInstalls.json`, more trustworthy than the four heuristic ones — games route through the Riot Client exe itself). `MainViewModel.ScanForGamesCommand` runs all 7 sources (Steam, Epic, Riot, GOG, Ubisoft, EA, Battle.net) through the shared `ImportScannedGames(IEnumerable<Game>)` dedupe/persist path — add new scanners there too, and to `ScanForGames()`'s `.Concat()` chain, rather than duplicating the merge logic or adding another header button (there's one "Scan for Games" button, not one per launcher — that got consolidated once the count hit 7). **Xbox/Microsoft Store is not implemented** — UWP/MSIX packages don't appear in the uninstall registry at all; would need `Get-AppxPackage`/`PackageManager` APIs, a genuinely different mechanism from every other scanner here.

There's also `Scanning/StandaloneExecutableScanner.cs` — finds games not registered with any launcher at all (the README's "standalone executables" feature) by scanning top-level `Program Files`/`Program Files (x86)` folders for a plausible main exe, blocking known launcher/vendor-hub folder names. This is a pure heuristic with no manifest or registry backing it, so unlike every other scanner it's **not** wired into auto-add — `MainViewModel.FindMoreGamesCommand` routes results through `ScanResultsWindow`/`ScanResultsViewModel`/`CandidateGameViewModel` (a real confirmation dialog, checkboxes default-checked) before anything reaches `ImportScannedGames`. If you add more heuristic (non-manifest) scanners, follow this same "confirm before adding" pattern rather than wiring them into `ScanForGamesCommand`. `CandidateGameViewModel.IsSelected` defaults to `false` — user opts into what's actually a game rather than opting out of false positives (changed from an initial default of `true`). `ScanResultsViewModel` has `SelectAllCommand`/`UnselectAllCommand` for bulk toggling in the dialog. Note: this scanner has no concept of DRM/license status — a cracked exe and a legitimately-purchased DRM-free game look identical to it, by design.

`Scanning/StandaloneExecutableScanner.cs`'s `DefaultScanRoots()` covers more than just the system drive: `Program Files`/`Program Files (x86)` on the system drive, plus `Program Files` and `Games` on every other fixed drive (`DriveInfo.GetDrives()`, `DriveType.Fixed`). Steam/Epic/Riot never needed this fix — they already read real install paths from registry/manifests, which work on any drive by construction.

`Scanning/ArtworkFetcher.cs` — downloads box art once for games with no local `ArtworkPath` and caches it to `%LocalAppData%\CartridgeOS\ArtworkCache\downloaded\{title}_{id}.jpg` (never re-fetched once cached). Steam games (appid parsed back out of the `steam://rungameid/{appid}` exe path) hit Valve's public CDN directly, no API key. Everything else is looked up by title, trying two sources in order: **SteamGridDB first**, **TheGamesDB as fallback** (capped at 1000 requests/month — exactly why it's not primary) — whichever returns null (no match, error, rate-limited) falls through to the next. **Both API keys are hardcoded constants** (`SteamGridDbApiKey`/`TheGamesDbApiKey` at the top of the file) — deliberately not env vars: this is closed-source, the key ships inside the compiled DLL of every install regardless of whether it's a literal or read from an env var, so an env var buys no real protection while adding a setup step that would silently break artwork for every new install. Same reasoning as the Discord Client ID in `DiscordRichPresence.cs` — if you ever open-source this repo, revisit all three. A private nested `RateLimiter` class tracks a per-source cooldown after an HTTP 429 (`Retry-After` header parsed, defaults to 60s if absent) — shared static state across every concurrent fetch in the process, since games are fetched fire-and-forget in a loop after a scan and a burst of many new games would otherwise hammer a source that just rate-limited us. While a source is cooling down it's skipped entirely (falls through immediately), never retried inline/blocking. Logs every step (cache hit, chosen source, non-2xx bodies, 429/backoff, download success/failure) to `%LocalAppData%\CartridgeOS\artwork.log`, plain append, no rotation. **Known weak spot**: both sources' title matching takes the first search result with no disambiguation, can pick the wrong regional/platform/remaster variant. Wired into `MainViewModel` in two places: `ImportScannedGames` (real scan results) and the constructor's initial DB load (so seed/demo games get artwork too) — both fire-and-forget per game via `GameDatabase.UpdateArtworkPath` + `GameTileViewModel.SetArtworkPath` hot-swapping the tile once art lands, never blocking the UI. `SteamScanner.FindArtwork` also got a bug fix here: was only checking the old flat `{appid}_library_600x900.jpg` filename, now checks the newer per-appid nested path (`librarycache/{appid}/library_600x900.jpg`) first — that's why Steam art wasn't showing even with a real local Steam install.

Also `Scanning/XboxScanner.cs` — Xbox app/PC Game Pass/Microsoft Store games. These are UWP/MSIX packages with no registry entry and no simple manifest file (unlike every other scanner), so this shells out to PowerShell's `Get-AppxPackage` (user picked this over native WinRT `PackageManager` interop or a narrower XboxGames-folder-only scan — see conversation history if the tradeoff needs revisiting) rather than reimplementing package-manager logic. Games launch via `shell:appsFolder\{PackageFamilyName}!{AppId}`. Same trust model as `StandaloneExecutableScanner` — no reliable "is this actually a game" signal, so it also routes through `ScanResultsWindow` confirmation, merged together in `MainViewModel.FindMoreGamesAsync` (now genuinely async — spawning PowerShell can take a couple seconds, and this used to run synchronously on the UI thread before Xbox scanning was added, which would now freeze the window). **Not tested against real Xbox/Store games** — by explicit user choice (no such install available), not just an oversight; only self-check-verified.

`MainViewModel` also runs a `DispatcherTimer` (15-minute interval, `ScanTrustedLauncherSources()`) that re-scans the 7 trusted launcher sources in the background — `RescanInBackgroundAsync` wraps the scan in `Task.Run` so it doesn't hitch the UI thread, merges back via the same `ImportScannedGames`. Deliberately excludes `StandaloneExecutableScanner` (would pop a confirmation dialog unprompted). `MainWindow`'s `Closed` handler calls `StopBackgroundRescanning()` — don't forget that if you ever add a second window/entry point that constructs a `MainViewModel`, or the timer outlives its owner.

## Tech decisions (already made — don't re-litigate)

- **UI framework: WPF**, not WinUI 3/Avalonia as the README's table originally suggested. Reason: user only has WPF available in their environment; WPF is sufficiently capable for a modern, fluid, hardware-accelerated fullscreen UI when paired with `WPF-UI` or `ModernWpfUI` for Fluent styling. See conversation history / progress.md for the reasoning.
- **Architecture per README's original diagram**: Windows Service (controller manager, input mapper, game scanner, config manager, IPC server) <-> Tray app <-> Fullscreen Launcher UI, talking over named pipes. **This has since diverged in one specific way (2026-08-07)**: Tray and Launcher were merged into one process (`CartridgeOS.Launcher.exe`) per explicit user request for Steam-style single-instance/tray-core/disposable-UI behavior — see the dedicated section below. The Service half of the diagram (controller manager, scanner, etc. living in a Windows Service) still hasn't happened; scanning/controller input still run inside Launcher. Don't "fix" the Tray/Launcher merge back apart without checking with the user first — it was deliberate, not drift.
- **Solution structure (current)**: `CartridgeOS.Core` (models, SQLite, scanning logic, IPC contracts), `CartridgeOS.Service`, `CartridgeOS.Launcher` (tray core + launcher UI, single process).
- **Data**: SQLite via `Microsoft.Data.Sqlite`, no ORM.
- **MVVM**: `CommunityToolkit.Mvvm` (source-generated, avoid handwritten boilerplate).
- **Controller input**: raw P/Invoke, no XInput NuGet wrapper (`Vortice.XInput`/`SharpDX.XInput` were considered, not used) — `Input/XInput.cs` calls `xinput1_4.dll` directly for Xbox-compatible pads. PlayStation/generic pads don't register with XInput at all, so `Input/RawGameControllerSource.cs` falls back to `Windows.Gaming.Input.RawGameController` (WinRT, DirectInput-backed) — see the dedicated section below for why the Launcher's TFM changed to support this.

## Efficiency constraints (non-negotiable, per user's "must not be slow" requirement)

- Game tile grid MUST be virtualized (`VirtualizingWrapPanel` NuGet, not a plain `WrapPanel`) — libraries can have hundreds of games.
- **Three-screen Home/Recently Played/Library system (2026-08-11), superseded the two-tab interface below.** `MainViewModel.SelectedScreen` (`AppScreen` enum: `Home`/`RecentlyPlayed`/`Library`, default `Home`) replaced `CurrentTab`; `EnumToVisibilityConverter` gates each screen. Nav bar is a centered pill `RadioButton` group (`NavTabStyle`), switchable via mouse, keyboard, or gamepad L1/R1 shoulder buttons (`GamepadAction.PreviousTab`/`NextTab`, `MainWindow.CycleScreen`). **Home**: PS5-style — selected game's own artwork fills the background (this is the only screen where selection drives the backdrop; top+bottom gradient fades keep header/title text legible), bottom-anchored title/details + an infinite horizontal carousel. The carousel is `MainViewModel.HomeCarouselSlots` — a plain computed `List<HomeCarouselSlot>` (game + `IsCenter` bool), bound to a bare `ItemsControl`+`DataTemplate`, **not** a `Selector`/`ScrollViewer`-based `ListBox` — that approach was tried first and kept silently failing to center/resize tiles correctly; the rewrite to explicit computed data was what actually fixed it (see progress.md 2026-08-11 for the failure history). **Recently Played**: hero "Continue Playing" card (highlights via `IsContinuePlayingGameSelected`) + 2x2 grid of the next 4 (`OtherRecentGames`) + a System Overview stats panel, plus an ambient drifting-particle `Canvas` background (`Views/RecentlyPlayedView.xaml.cs`, `TranslateTransform`+`DoubleAnimation`, no dependency — see the particle-bug note below if touching this). **Library**: unchanged virtualized grid.
- **View-layer split into `Views/` (2026-08-11)**: `MainWindow.xaml`/`.xaml.cs` had grown past 1000/300 lines holding markup+handlers for all four screens. Split into `Views/HomeView`, `Views/RecentlyPlayedView`, `Views/LibraryView`, `Views/SettingsPanel` — plain `UserControl`s with **no `DataContext` of their own**, so they inherit `MainViewModel` from the Window and every existing `{Binding ...}` kept working unchanged. `MainWindow` is now a thin shell (~190 lines): background layer, header/nav bar, and `<views:HomeView/>` etc. hosts gated by the same `EnumToVisibility` bindings the inline screen `Grid`s used to have. `LibraryView` exposes `public ListBox GameGrid` since `MainWindow.HandleGamepadAction`'s column-math nav and `OpenGameContextMenu` still need to reach it from the shell. **`MainViewModel` was deliberately NOT split** — almost every property on it (`SelectedGame`, `SelectedScreen`, `Games`/`GamesView`) is genuinely shared across 2+ screens; splitting it would need a new state-sharing mechanism (messenger/mediator) that doesn't exist, for unclear benefit. Shared styles used by 2+ screens live in `Styles/SharedStyles.xaml`; a style used by exactly one screen lives in that screen's own `UserControl.Resources`. **`SharedStyles.xaml` is merged into `App.xaml`'s `Application.Resources`, NOT `MainWindow.xaml`'s `Window.Resources`** — this matters: a `UserControl`'s `InitializeComponent()` resolves `StaticResource` lookups *before* it's attached to its parent's visual tree, so a Window-level merged dictionary isn't visible yet at that point and any UserControl-local style referencing it throws `Cannot find resource named '...'` at startup. App-level resources don't have that timing problem — if you ever add a new cross-screen shared resource, put it in `Styles/SharedStyles.xaml`/`App.xaml`, not `MainWindow.xaml`.
- **Recently Played particle background gotcha**: the drift-loop `StartDrift` originally read `From = transform.Y` when restarting each cycle — but WPF holds an animated property at its final value after the animation completes (no `FillBehavior.Stop`), so that read returned the *previous cycle's `To`*, making `From == To` on every restart after the first (particles silently froze instead of respawning). Fixed by threading the start offset through as an explicit parameter instead of reading the animated property back. If you touch animation-restart-on-`Completed` code anywhere else in this app, this is the failure mode to check for first.
- Artwork must be decoded at target size (`BitmapImage.DecodePixelWidth`) and disk-cached, never loaded full-res per tile.
- Animate only `RenderTransform`/opacity (GPU-composited), never layout properties (`Width`/`Height`/`Margin`).
- All scanning/file IO off the UI thread.

## Single-instance launcher, tray core, disposable UI (2026-08-07)

Built per an explicit, detailed user spec: single-instance app, a persistent lightweight tray/core half and a disposable launcher-UI half, memory released when the UI closes. This is the reason `CartridgeOS.Tray` no longer exists as a separate project — it's now `App.xaml.cs` inside `CartridgeOS.Launcher`.

**Single instance**: `App.OnStartup` takes a `Mutex(@"Global\CartridgeOS.SingleInstance")`. If another process already holds it, this process sends a `"ShowLauncher"` request over a dedicated named pipe (`CartridgeOsPipeServer`/`Client`, pipe name `"CartridgeOS.Launcher.SingleInstance"` — **not** the same pipe as the Service's IPC below, `CartridgeOsPipeServer`'s pipe name is now a constructor parameter defaulting to `CartridgeOsPipeServer.DefaultPipeName` so both can coexist) and exits immediately (`Environment.Exit(0)`) — no window, no tray icon, nothing else happens in that process. The primary instance's `HandleSingleInstanceSignal` dispatches the request onto the UI thread and calls `ShowLauncher()`.

**Core vs disposable UI**: `App` owns everything that must survive the launcher window being closed — `GamepadWatcher`, `MouseEmulator`, `GlobalHotkey`, `DiscordRichPresence`, running-game process tracking, and the whole overlay flow (`ToggleOverlay`/`ReturnToLauncher`/`QuitRunningGame`, moved here from `MainWindow.xaml.cs`). `GlobalHotkey` needs a real native window handle to register `RegisterHotKey` against; since the launcher window can be destroyed at any time, `App` creates a small always-alive, never-shown `_coreWindow` (`Width=0 Height=0 Visibility=Hidden`) purely for this, via `WindowInteropHelper.EnsureHandle()` (not `.Handle`, which returns zero for a window that's never been shown — `GlobalHotkey.cs` was changed to use `EnsureHandle()` to support this). Gamepad action routing also moved to `App`: it subscribes to `GamepadWatcher.ActionPressed` once, handles `GamepadAction.Menu` (toggle overlay) itself, and forwards everything else to `_launcherWindow?.HandleGamepadAction(action)` when a window exists. (As of 2026-08-08 this is `GamepadAction`, not the raw `GamepadButton` this paragraph originally described — see the PlayStation-controller/input-normalization section above.)

`MainWindow.xaml.cs` is now genuinely disposable: no long-lived service references of its own. `App.ShowLauncher()` constructs it (passing the last-selected game's id so it can restore the selection) when `_launcherWindow` is null, or just restores/activates the existing one otherwise — this single method is the answer to "open the launcher" from every caller: initial startup, tray icon click/double-click, the single-instance pipe signal, the overlay's "Return to Cartridge OS" button, and auto-reopen on game exit. `App.OnLauncherClosed()` (wired to the window's `Closed` event, which fires for the X button, Alt+F4, or a programmatic `Close()` — `ShutdownMode="OnExplicitShutdown"` in `App.xaml` means none of those quit the app) captures `_lastSelectedGameId`, drops the window reference, then does one deliberate `GC.Collect()` + `GC.WaitForPendingFinalizers()` pass. That GC call is intentional, not an accident to clean up later: WPF `BitmapImage` isn't `IDisposable`, so there's no per-object dispose loop to write for the freed artwork/decoded images — dropping every reference to the closed window/viewmodel/`GameTileViewModel` graph and forcing a collection *is* the correct way to reclaim that memory promptly instead of waiting for whatever GC happens to run next.

`LaunchGame` (moved off `MainWindow.LaunchSelected`, which now just forwards to `((App)Application.Current).LaunchGame(vm, game)`) starts the process, sets Discord presence, and — **user's explicit choice**: minimizes rather than destroys the launcher window on launch (cheaper, no recreate-flicker; the window can still be fully closed independently via the X button while a game runs, same `OnLauncherClosed` path as any other close) — tracks the process for the overlay, and on exit (`OnGameExited`) clears Discord presence and calls `ShowLauncher()` again automatically (**user's explicit choice**: Steam-like auto-reopen, not stay-closed).

Tray context menu is now just **Open Cartridge OS** / **Exit Cartridge OS** — the old Tray project's "Service Status" item was dropped rather than ported, since mixing the separate/still-unused Service's status into this merged app's menu didn't make sense once Tray and Launcher were the same process. `ExitApplication()` (wired to "Exit Cartridge OS") is the only path that actually calls `Shutdown()` — it cancels the single-instance pipe server, stops the gamepad poll loop, disposes the hotkey/Discord connection, closes the overlay and launcher window, disposes the tray icon, closes the core window, and releases+disposes the mutex, in that order.

**Verified hands-on** (via PowerShell + raw Win32 calls, working around this environment's UI-automation limitation — see below): started the app (one process) → ran the exe again (second process exited immediately, code 0, no duplicate) → sent `WM_CLOSE` via `PostMessage` to the real window handle found through `EnumWindows`/`GetWindowThreadProcessId` (`Get-Process.MainWindowHandle` came back `0` for this borderless/topmost window and couldn't be used directly) → confirmed the window closed but the same PID kept running → ran the exe again → confirmed the *same* process's window reopened. All four core requirements confirmed working, not just compiling. **Not verified by hand**: tray icon visual appearance/context-menu clicks (can't click a real tray icon from here), and the overlay/Discord-presence flow during an actual running game.

## Named-pipe IPC (Service <-> Launcher, and Launcher <-> Launcher for single-instance)

`Core/Ipc/` has a real, working named-pipe transport: `PipeFraming.cs` (length-prefixed UTF-8 framing), `PipeMessages.cs` (`PipeRequest`/`PipeResponse` records), `CartridgeOsPipeServer.cs` (one connection handles exactly one request then closes — not a long-lived duplex session; `pipeName` is a constructor parameter, defaults to `DefaultPipeName`), `CartridgeOsPipeClient.cs` (`SendAsync`, also takes an optional `pipeName`, returns `null` on any failure — nothing listening, timeout, busy — never throws). All IPC classes use `ConfigureAwait(false)` throughout; don't remove it, see the WPF-deadlock note above — the same class of bug bit this code too, before it ever shipped.

`CartridgeOS.Service`'s `Worker.cs` hosts a server on the default pipe name, backed by the actual shared `GameDatabase` (same `%LocalAppData%\CartridgeOS\games.db` the Launcher uses) — `Ping` and `GetGameCount` are real commands, not stubs, reachable via `--ipc-ping` from the Launcher. **Separately**, `App.xaml.cs` hosts a second server on its own pipe name (`"CartridgeOS.Launcher.SingleInstance"`) purely for single-instance signaling — see the section above. These two servers are unrelated; don't conflate them.

**Scope note — the transport is real, the Service-side architecture migration is not.** The README's architecture diagram shows Controller Manager/Input Mapper/Game Scanner/Configuration Manager all living in the Service, with the Launcher talking to them over this pipe. That has **not** happened — scanning (`Core/Scanning/*`) and controller input (`Input/GamepadWatcher.cs`, now owned by `App`) still run directly inside the Launcher process. Migrating that ownership into the Service is a much bigger, separate piece of work (would need to redesign how the Launcher's UI stays in sync with Service-owned state — polling? a persistent duplex connection instead of one-request-per-connection? push notifications on scan completion?) and hasn't been scoped yet. If you pick that up, decide on the sync model first — the current one-shot request/response server as built doesn't support server-initiated push, only client-initiated pull.

Testing note: `Microsoft.Data.Sqlite` pools connections by default — `Dispose()` doesn't release the underlying file handle. Any code (tests, scripts) that creates a temp SQLite file and needs to delete it afterward must call `Microsoft.Data.Sqlite.SqliteConnection.ClearAllPools()` first, or the delete will fail with a sharing violation. `Services/PipeIpcSelfCheck.cs` in Launcher hit this.

## Boot splash screen (2026-08-12)

Steam-style splash shown at startup, per a detailed user spec: dark background, the logo mark traces itself in (outer shell, then inner diamond/d-pad lines), glow builds while it draws, a solid fill lands on top, then the wordmark slides/fades in. `SplashWindow.xaml`/`.xaml.cs` (project root, alongside `OverlayWindow`/`ScreenSaverWindow` — not `Views/`, same reasoning as those). Reuses `assets/logo/cartridge.svg`'s logo-mark path data **verbatim** as WPF `PathGeometry.Figures` strings — WPF's Path markup mini-language is SVG-path-syntax-compatible (M/L/C/Q/Z all supported), so no re-derivation was needed.

**Stroke-reveal mechanic**: WPF has no native SVG-style `stroke-dashoffset` trim-path animation, so it's faked with the standard trick — `StrokeDashArray = [length, length]`, animate `StrokeDashOffset` from `length` to `0`. The one non-trivial part is getting `length` right: WPF has no direct "geometry length" API either, so `SplashWindow.xaml.cs`'s `GeometryLength` flattens the path (`Geometry.GetFlattenedPathGeometry`) into line segments and sums the distances between consecutive points — good enough at a reasonable tolerance (0.25), doesn't need to be exact since it's immediately fed back into that same shape's own dash array.

**Animation timeline** (~2.6s total, built via `Storyboard`/`DoubleAnimation`s in code-behind, not XAML triggers, since several durations/begin-times are relative to each other): background fade-in (0-150ms) → outer shell + glow trace (0-850ms, `StrokeDashOffset`) → inner diamond/lines trace, staggered (650-1300ms) → whole mark scales past 1.0 then settles (`BackEase`, 0-1200ms) → solid fill fades in on top of the now-complete trace (1250-1850ms) → wordmark slides in from the left + fades (1750-2250ms). `AnimationCompleted` event fires when the `Storyboard` finishes; `App.xaml.cs`'s `ShowSplashThenLauncher` (called from `OnStartup` in place of the old direct `ShowLauncher()` call) waits for that event, then calls `ShowLauncher()` and closes the splash.

**Real bug hit and fixed — blur scoping**: the intro blur-to-sharp effect originally wrapped the *entire* logo lockup (mark + wordmark) in one `BlurEffect` on their shared parent `Grid`. User reported "this is very blurry" with a screenshot showing the wordmark permanently soft. Root cause, not just "the blur radius was too high": applying **any** WPF pixel-shader `Effect` to a `TextBlock` disables ClearType/sub-pixel text hinting — the text reads visibly blurrier than un-effected text even once the animated radius reaches `0`, because the `Effect` object being *attached at all* forces off-screen shader compositing for that element, which is a separate cost from the blur radius itself. Fixed two ways together: (1) scoped the `BlurEffect` to just the logo-mark `Canvas`, never the `Wordmark` `StackPanel`/`TextBlock`s; (2) once the intro blur-clear `DoubleAnimation` completes, its `Completed` handler sets `LogoMark.Effect = null` outright, fully detaching the effect rather than leaving it attached at `Radius=0`. **If any future animation in this app needs a blur-then-sharp text reveal, don't put text inside the blurred element at all — animate a separate un-effected text layer's opacity/position instead.**

**Whoosh sound**: `assets/splash/whoosh.mp3` (user-supplied) copied to `src/CartridgeOS.Launcher/Assets/Splash/whoosh.mp3`, `Content`/`CopyToOutputDirectory` in the csproj. Played via `System.Windows.Media.MediaPlayer` (WPF's built-in mp3-capable player, same one `ScreenSaverWindow` already uses for its background music) — **not** `SoundService`/`System.Media.SoundPlayer`, which is wav-only and can't play mp3 at all. Triggered at the very start of `BeginAnimation()`, so it lands right as the trace starts drawing. Same guard-and-swallow pattern as every other sound path in this app (`SoundService`, `ArtworkFetcher`, etc.) — a missing/corrupt file can't break the splash.

Shown for a **fixed** duration regardless of how long the rest of startup actually takes — this is a brand beat, not a progress indicator, and deliberately doesn't try to track real load state (`MainWindow`'s construction, which can hit the DB, happens to overlap with the splash's ~2.6s runtime rather than being explicitly synced to it). `ponytail`-marked in the class doc comment: add a progress-driven variant only if a slow first-run scan actually makes the fixed duration feel wrong in practice.

## Home carousel: from "computed slot list" to a real sliding carousel (2026-08-12)

**Supersedes** the Home-carousel description in the "Efficiency constraints" bullet further up this file (that description — "plain computed `List<HomeCarouselSlot>`... not a `Selector`/`ScrollViewer`" — is now only half-accurate; the "not a Selector/ScrollViewer" part is still true and still the right call, but it's no longer a freshly-recomputed plain list). User reported the carousel's scrolling felt "jerky," which turned out to be two different, sequential bugs once the first fix exposed the second:

**Bug 1 — full teardown/rebuild every nav step.** `MainViewModel.HomeCarouselSlots` used to be a computed property returning a brand-new `List<HomeCarouselSlot>` (`record`, `Game` + `IsCenter`) every time `SelectedGame` changed. Since `IReadOnlyList<T>`-typed `INotifyPropertyChanged` bindings have no concept of "this specific item changed" the way `ObservableCollection` does, WPF treated every `PropertyChanged` on `HomeCarouselSlots` as "the whole `ItemsSource` is a new collection" — full `ItemContainerGenerator` reset, all 7 tiles destroyed and recreated on **every single Left/Right press**, replaying the per-tile pop-in animation across the whole row simultaneously each time with zero interpolation between old/new state. That's what actually read as "jerky." Fix: `HomeCarouselSlot` became a mutable `ViewModelBase`-derived class (`[ObservableProperty]` `Game`/`IsCenter`), `HomeCarouselSlots` became one persistent `ObservableCollection` instance that `RefreshHomeCarouselSlots` mutates in place instead of replacing.

**Bug 2 — position-keyed slots never actually move.** That fix alone wasn't enough: user reported back "the center border is fixed and images are just changing, doesn't feel like they're moving left/right or resizing." Root cause: the mutate-in-place fix kept mapping "offset from center" to a **fixed array index** (slot index 3 of 7 was always written as `IsCenter = true`, indices 0/6 always `false`) — so a given container's `IsCenter` value literally never changed across nav steps, meaning its resize/reposition trigger never had a reason to fire; only the bound `Game` content swapped in place, which reads as a content flip, not a slide. Fixed by re-keying `HomeCarouselSlot` around a **game**, not a position: `Game` is now fixed at construction (never reassigned), and a new mutable `Offset` (distance from center, can be any value in `-side..side`) is what changes over time. `MainViewModel.RefreshHomeCarouselSlots` now diffs old vs. new window membership by game identity (`Dictionary<GameTileViewModel, HomeCarouselSlot>`) — a game staying in the window just gets its `Offset` updated (this is what has something real to animate now); only games newly entering/leaving the visible window get added/removed from the collection. The carousel's `ItemsPanel` changed from a `StackPanel` to a `Canvas` (`Views/HomeView.xaml`, fixed size `1750x360` — see the pitch-spacing note below for where those numbers come from), since tiles are now absolutely positioned by `Offset`, not laid out left-to-right by document flow. `Views/HomeView.xaml.cs`'s `ApplyOffset` maps `Offset → (width, height, X, Y)` and, on every `HomeCarouselSlot.PropertyChanged` for `Offset`, animates all four via `BeginAnimation` (340ms `CubicEase`) — this is what makes a tile genuinely slide sideways and grow/shrink as its distance from center changes, instead of a fixed container's content just swapping.

**Bug 3 — Canvas.Left/Top on the wrong element.** Reported with a screenshot: "everything is in the left corner," tiles stacked on top of each other. `Canvas.Left`/`Canvas.Top` only position a `Canvas`'s **direct children** — when a `Canvas` is used as an `ItemsControl`'s `ItemsPanel`, WPF wraps each data item in a `ContentPresenter`, and *that* is the Canvas's real direct child; the `DataTemplate`'s own root element (the `Border` named `Tile`) sits one level deeper inside it. `ApplyOffset` was calling `Canvas.SetLeft(tile, ...)` on that inner `Border` — which the `Canvas` never looks at — so every tile defaulted to `(0,0)`. Fixed by walking up via `VisualTreeHelper.GetParent(tile)` in `HomeCarouselTile_Loaded` to get the actual `ContentPresenter`, and positioning *that* (`Width`/`Height` still animate on `tile` itself, since those genuinely are the `Border`'s own size). **If a future Canvas-hosted `ItemsControl` needs per-item position, remember `Canvas.Left`/`Top` must target the generated container, not the `DataTemplate` root — this exact mistake is easy to repeat.**

**Follow-up polish — spacing.** Once tiles were actually sliding, the user asked for more visible gap between the center tile and its neighbors (they read as touching/overlapping at the original spacing). `SlotPitch` (horizontal distance between adjacent offsets' centers) went from 210→250px; the backing `Canvas`'s fixed `Width` went from 1470→1750 to match (`(2*HomeCarouselSideCount+1) * SlotPitch`, `HomeCarouselSideCount` is `internal const int = 3` on `MainViewModel`, mirrored as a comment in `HomeView.xaml.cs` — **keep these two in sync if either changes**).

**Not hands-on verified against real game data at any step** — every fix in this sequence was verified by (a) reading the code for the specific mechanism WPF uses (container generation, `Canvas` positioning rules) and (b) confirming the app still launches without crashing; the actual on-screen "does it look right" feedback for all three bugs came from the user's own screenshots each round, not from anything observable in this environment.

## Recently Played selected-card Ken Burns zoom (2026-08-12) — REVERTED, see "Whole-card selection transition" below

User asked for a slow ambient zoom on whichever card's artwork is currently selected on Recently Played, "like in slideshows." Both the hero card and the 2x2 grid rows' artwork already had their `RenderTransform` spoken for by the existing launch-zoom trigger (`IsLaunching` → scale to 1.18), so the actual artwork moved one level deeper into a new inner `Border` (`HeroArtworkKenBurns` on the hero, `ArtworkKenBurns` in `RecentRowStyle`) with its own separate `ScaleTransform` and its own self-contained `Style`/`DataTrigger`, rather than reusing the outer element's trigger — two triggers animating the same transform would otherwise fight.

**Two real bugs, both only surfaced by the user's own testing, not by build or code review**: (1) the first version used an explicit `From="1.12"` on the `DoubleAnimation` — WPF applies an explicit `From` as an instantaneous jump to that value the moment the trigger's `EnterActions` fires, *before* the animation itself starts easing away from it. So the "zoom out" (1.12 → 1.0) was correct and slow, but getting to 1.12 in the first place was an instant snap, which read as "the zoom-in is very fast." Fixed by dropping `From` entirely — a `DoubleAnimation` with only `To` set animates from whatever the property's current value already is, so it starts from `1.0` (the XAML-declared value) with no discontinuity. (2) even after that fix, the user reported "no animation in any card" — turned out to be `SineEase EasingMode="EaseInOut"`, which has a near-zero derivative right at the start/end of its curve; over the original 14-second duration, the first several seconds of motion were too small to perceive, indistinguishable from "not animating" during a quick glance (confirmed the trigger *was* actually firing by checking the border-highlight, which shares the same underlying selection binding and was visibly correct). Switched to `EaseOut` (movement starts immediately) and shortened the duration to 9s. **If a future ambient/idle animation in this app needs to feel obviously "on" from the moment it starts, avoid `EaseInOut` — use `EaseOut` or no easing function at all.**

## Discord Rich Presence (Phase 3, started 2026-08-07; moved from MainWindow to App on 2026-08-07)

`Services/DiscordRichPresence.cs` talks to Discord's local IPC pipe directly (`\\.\pipe\discord-ipc-{0..9}`, handshake + `SET_ACTIVITY` frames) — no `discord-rpc` dependency. `ClientId` is the real registered Application ID (`1535179486117502976`, not a secret — shared by every Cartridge OS install).

**Debugged 2026-08-08 after the user reported it didn't work on a second PC.** Two real bugs, found by reading the code (no Discord available to test against directly in this environment): `ConnectAsync` read the handshake response frame but never looked at its contents before setting `_ready = true` — Discord replies to a rejected handshake (e.g. bad/unrecognized `ClientId`) with `evt:"ERROR"` rather than closing the pipe, so a rejected handshake was indistinguishable from a successful one and every subsequent activity update silently failed. Added `%LocalAppData%\CartridgeOS\discord.log` (`Log()`, same plain-append-no-rotation pattern as `Core/Scanning/ArtworkFetcher.cs`'s `artwork.log`) logging every pipe-connect attempt, the handshake response, and every `SET_ACTIVITY`/clear response — this class had *zero* logging before, which is exactly why "it didn't work" on a second PC was undiagnosable without this fix. Verified the logging mechanism itself works (confirmed `discord.log` gets the correct "no pipe found" line when Discord isn't running, which is the case in this dev environment). **Still not verified against a real running Discord client** — next step if it's still not working after this: check the actual contents of `discord.log` on the machine where it fails. If the handshake response line shows `evt:"ERROR"`, the attached message says why; the most likely single cause is the registered Discord application behind `ClientId` (`developer.discord.com/applications`) no longer existing, being misconfigured, or `ClientId` itself being stale/wrong — that's something to verify directly on the Developer Portal, not something fixable from reading this repo's code alone.

Now owned by `App` (was `MainWindow`) so it survives the launcher window being closed: connects in `App.OnStartup` (fire-and-forget, silently no-ops if Discord isn't running), sets activity right after every game launch via `App.LaunchGame` — including Steam/Xbox shell-launches, since setting activity doesn't need the `Process` handle the way overlay tracking does — and clears it in `App.OnGameExited`, which is only reachable for the subset of launches that do produce a trackable `Process` (see the overlay section above for which those are). So: Steam/Xbox presence will show "Playing X" but won't auto-clear when that game closes, since we have no signal for when it does.

Suspend/Resume (the Phase 3 item before this one) was evaluated and explicitly **not built** — see the 2026-08-07 progress.md log entry for the full reasoning (real console-style suspend isn't possible on Windows for arbitrary processes; the only achievable version is freezing threads via undocumented `NtSuspendProcess`, which risks anti-cheat bans in online games). ## Two launch/scan bugs fixed 2026-08-08, both reported by the user hands-on

**Games launched with the wrong working directory**: `App.LaunchGame`'s `ProcessStartInfo` never set `WorkingDirectory`, so it defaulted to the .NET process's own folder (the Launcher's own `bin\...`). ## Artwork crop/reposition (2026-08-08)

Follow-up to "Change Wallpaper" above: the tile's `Image` uses `Stretch="UniformToFill"`, which auto-crops to fill — fine for artwork that's already roughly the tile's shape, but silently centers the crop for anything else, which can cut off the interesting part of an unrelated-aspect-ratio image with no user control. `ArtworkCropWindow.xaml`/`.xaml.cs` fixes that: a 300x450 (2:3) viewport the user pans (drag) and zooms (slider, clamped to never zoom out past fully covering the viewport — a deliberate "cover" constraint, not a bug, so there's never an empty gap at an edge) before confirming. On confirm it computes the source-pixel crop rect from the current `ScaleTransform`/`TranslateTransform` values, crops via `CroppedBitmap`, and writes a new PNG to `%LocalAppData%\CartridgeOS\ArtworkCache\custom\{guid}.png` — a plain code-behind dialog (`DialogResult`/`ResultPath`, same shape as the existing `ScanResultsWindow`), no separate ViewModel, since this is inherently view-state (drag position, zoom level) with no other consumer.

`MainViewModel.ChangeArtwork()` only opens this dialog when the picked file's aspect ratio is more than 5% off the 2:3 target (`MatchesTileAspect`/`TileAspect`/`AspectTolerance` constants) — checked via `BitmapFrame.Create(uri, BitmapCreateOptions.DelayCreation, BitmapCacheOption.None)`, which reads just the image header for `PixelWidth`/`PixelHeight` without a full decode, cheap enough to run synchronously on the UI thread for a single file. An image that's already close to the tile's shape skips the crop step entirely and uses the picked file as-is — no forced extra click for the common case of art that's already sized right.

**Not hands-on verified** — no way to drag a mouse, see rendering, or confirm the crop math is pixel-accurate from this environment. If the crop looks off after real use: the likely culprit is the `2.0/3.0`/300x450 viewport constant not actually matching the live tile artwork slot's real rendered aspect ratio (never precisely measured at runtime, just approximated from the box-art convention other parts of this app already assume) — `Stretch="UniformToFill"` on the tile will still auto-crop-to-fill regardless of small mismatches, so it's a "slightly wrong center point" risk, not a broken-image risk.

## Artwork revert (2026-08-08)

Follow-up to the two artwork sections above, prompted by the obvious next question: what if the user changes a game's artwork and doesn't like it? `GameTileViewModel` now remembers one prior `ArtworkPath` (`_previousArtworkPath`/`_hasPreviousArtwork`, set inside `SetArtworkPath` right before overwriting) and exposes `TryRevertArtwork(out restoredPath)` to restore-and-forget it — deliberately a **single undo level, not a history stack**: reverting twice in a row does nothing on the second call. "Revert to Previous Artwork" sits in the same context menu as "Change Wallpaper"/"Delete Game" (`MainWindow.xaml`'s `GameTileContextMenu`), same code-behind-`Click`-handler pattern as those two.

`GameDatabase.UpdateArtworkPath`'s parameter became `string?` (was `string`) to support reverting a game that had no artwork at all before its most recent change — writes `DBNull` on null. `TryRevertArtwork` also explicitly nulls the viewmodel's `Artwork` property in that case, since `GameTileViewModel.LoadArtworkAsync` intentionally no-ops on a null/empty `ArtworkPath` (early-return, doesn't clear the previously-loaded bitmap) — without that explicit null-out, reverting-to-nothing would leave the old image showing.

**Important scope limit, not an oversight**: the "previous artwork" memory lives only on the in-memory `GameTileViewModel` for the current window session. Since the launcher window (and its whole viewmodel graph) is disposable and gets destroyed/recreated on close/reopen (see the single-instance/tray-core section), this memory does not survive that — closing and reopening the launcher, or restarting the app, forgets what the "previous" artwork was. If cross-session undo is ever wanted, it would need a real column/history table in `GameDatabase`, not just an in-memory field — hasn't been asked for, don't build it speculatively.

Fixed with two **implicit** styles in `MainWindow.xaml` — `<Style TargetType="ContextMenu">` and `<Style TargetType="MenuItem">`, deliberately no `x:Key` — so they apply automatically to any menu anywhere in the app (there's only the one today, but this makes a second one theme-correct for free rather than needing its own explicit `Style=` reference). `ContextMenu`'s template is a rounded `SurfaceRaisedBrush` `Border` with a `DropShadowEffect`; `MenuItem`'s template drops the native icon/check gutter entirely (every item here is a plain text action, nothing ever gets a checkmark or icon) in favor of a flat `Border` that highlights `SurfaceHoverBrush` on `IsHighlighted`. This is a general app-wide default, not scoped to `GameTileContextMenu` specifically — keep that in mind if a future menu ever needs icons/checkable items, since the current `MenuItem` template has nowhere to put them and would need a second, non-implicit style for that case rather than fighting this one.

**Not visually verified** — no screenshot capability here; open the context menu by hand and confirm it reads as part of the app now, not as a stock Windows menu.

## Context menu item enabled/disabled state (2026-08-08)

"Revert to Previous Artwork" used to always be clickable, silently no-opping via `TryRevertArtwork`'s `false` return when there was nothing to revert — user asked for it to actually be disabled instead. `GameTileViewModel.HasPreviousArtwork` went from a private field to a public property for this. `MainWindow.xaml`'s `GameTileContextMenu` gained `Opened="GameTileContextMenu_Opened"`: reads `((ContextMenu)sender).PlacementTarget`'s `DataContext` (the `GameTileViewModel` the menu is opening for — set natively by right-click, or explicitly by `MainWindow.OpenGameContextMenu` for the gamepad path, so this one handler covers both), finds the specific `MenuItem`, and sets its `IsEnabled`.

**First attempt used `menu.FindName("RevertArtworkMenuItem")` and didn't work** — the user reported the item was "still the same" (always clickable) after it shipped. Root cause: a `MenuItem` declared with `x:Name` inside a `Window.Resources` object graph (as opposed to inside a `ControlTemplate`, which auto-creates a `NameScope`) is **not** registered anywhere `FindName` can resolve at runtime — `FindName` silently returned `null`, so the `if` guarding `IsEnabled` never ran, and the item just kept its XAML-default `IsEnabled="True"` forever. Nothing threw, nothing looked wrong in the diff — this is exactly the kind of bug that survives a build-clean/app-runs smoke test and only surfaces from an actual click. **Fixed with a `Tag`-based lookup instead**: `Tag="RevertArtwork"` in XAML, `menu.Items.OfType<MenuItem>().FirstOrDefault(mi => Equals(mi.Tag, "RevertArtwork"))` in code-behind — `menu.Items` enumeration works regardless of naming/`NameScope`, since these are literal `MenuItem` objects already present as `Items`, not generated from a `DataTemplate`. **If a future context/popup menu in this app needs to reach a specific item from code-behind, use `Tag` + `Items` enumeration, not `x:Name`/`FindName`, unless it's genuinely inside a `ControlTemplate`.**

The custom `MenuItem` template from the theming pass above (see "Context menu theming") had no disabled-state visuals at all — WPF doesn't give you that for free once you replace the default `ControlTemplate`. Added an `IsEnabled="False"` trigger: muted-gray text (`TextMutedBrush`), the hover-highlight `Setter` overridden back to transparent (otherwise a disabled item could still light up gray on mouse-over, which reads as "actually clickable"), and an arrow cursor instead of the hand cursor every other menu item uses.

## Modal-dialog gamepad routing + crop dialog controller support (2026-08-08)

The artwork crop dialog (see above) was mouse-only — user asked for controller support. This surfaced a real gap in the input-normalization work: `GamepadWatcher.ActionPressed`/`RightStickMoved` were wired straight from `App` to whichever the launcher window / mouse-cursor-emulation, with no concept of "something modal is currently on top and should own input instead." Fixed generally, not just for this one dialog:

**New `Input/IGamepadInputTarget.cs`** (`HandleAction(GamepadAction)`, `HandleRightStick(float, float)`) + **`App.SetModalGamepadTarget(IGamepadInputTarget?)`**. While a target is set, `App.OnGamepadAction`/`OnRightStickMoved` route there exclusively instead of `_launcherWindow`/the mouse-emulation cursor, and `OnRightTriggerChanged` suppresses the emulated click entirely (avoids a stray click landing on whatever's underneath). `App`'s `MouseEmulator` and the `RightStickMoved`/`RightTriggerChanged` subscriptions had to move from `OnStartup` locals/inline lambdas to a field (`_mouse`) and named handler methods to support the branch — any future modal window that wants gamepad input follows the same two-line pattern `ArtworkCropWindow` uses: `Loaded += (_, _) => ((App)Application.Current).SetModalGamepadTarget(this);` / `Closed += (_, _) => ((App)Application.Current).SetModalGamepadTarget(null);`, and implement the two interface methods.

**`ArtworkCropWindow`'s actual control scheme** deliberately reuses existing `GamepadAction`/stick plumbing rather than adding new physical-button support: right stick pans directly (same physical stick as mouse-cursor emulation, just a different meaning while this dialog owns input — no on-screen cursor involved here); D-pad up/down zooms via `GamepadAction.NavigateUp`/`NavigateDown`, which `GamepadWatcher` already fires with repeat-while-held, so holding a direction zooms continuously with zero new repeat-timer code; `Confirm`/`Back` map to the same "Use This Crop"/"Cancel" logic the mouse buttons call. There was no way to add analog-trigger or shoulder-button (LB/RB) zoom without extending `GamepadButton`/`XInputGamepad` bit-reading, which wasn't worth it when D-pad zoom was already free.

**Not hands-on tested with a physical controller** — same standing caveat as the rest of the gamepad code. `StickPanPixelsPerTick`/`DPadZoomStepFactor` (`ArtworkCropWindow.xaml.cs`) are unverified-by-feel constants, most likely to need adjustment once someone actually uses this with a controller.

## Minimize-on-launch bug for shell launches (2026-08-08)

Pre-existing bug, not introduced by anything in this session — the user hit it right after the "Launching..." indicator shipped, which is what surfaced it. `App.LaunchGame`'s `_launcherWindow.WindowState = WindowState.Minimized` call lived inside the `if (process is not null) { ... }` branch — meaning it **only ever ran for directly-tracked exe launches**, never for Steam/Xbox shell launches (`Process.Start` returns `null` for `steam://rungameid/...`/`shell:appsFolder\...`, which is correct and already documented behavior — the bug was gating the minimize call on that too, when the two things are unrelated). Result: launching anything through Steam or the Xbox app left the fullscreen, `Topmost="True"` launcher sitting visually on top of the game that had just started, with no indication anything had gone wrong (the game likely did start, just hidden behind the launcher). Fixed by moving the minimize call to run unconditionally, immediately after `Process.Start`, before the null check — every launch path now gets the same "get out of the way" behavior regardless of whether there's a `Process` to track afterward. **Not hands-on verified against a real Steam/Xbox launch** — no such install available in this environment.

## "Launching..." tile indicator (2026-08-08)

User reported clicking a game repeatedly because nothing indicated a launch had registered — worst for shell launches (Steam/Xbox), where `Process.Start` returns `null` immediately and the real game window can take several seconds to appear, with zero feedback in between. `GameTileViewModel.IsLaunching` (new `[ObservableProperty]`) drives a darkened full-tile overlay + "Launching..." label, added to both `GameTileStyle` and `RecentTileStyle` in `MainWindow.xaml`.

All of this routes through `App.LaunchGame` — already the single launch entry point every trigger path (gamepad Confirm, Enter/Space, double-click) funnels through, per the original single-instance/tray-core design — so this needed exactly one guard, not one per caller: `if (game.IsLaunching) return;` right at the top answers "repeat clicks" directly. Clearing the flag is based on what's actually knowable: a real `Process` back from `Process.Start` means the OS genuinely launched it, so it clears immediately (no guessing needed); a shell launch (`Process` is `null`) has no such signal at all, so it clears after a fixed `ShellLaunchIndicatorTimeout` (6s) instead — a real, if imprecise, tradeoff, not a bug: there's no reliable way to know when a `steam://`/`shell:appsFolder\...` launch actually produced a visible window, this app has hit that exact wall before (see the in-game-overlay section above, "known limitation, not a bug to fix casually").

**Hit a real XAML forward-reference crash while wiring this up**: `BoolToVisibility` (and the other two converters) were declared in `Window.Resources` *after* `GameTileStyle`/`RecentTileStyle`, and the new overlay's `Visibility` binding inside those styles' `ControlTemplate`s references `BoolToVisibility` via `StaticResource` — which, unlike `DynamicResource`, requires the resource to already be defined **earlier in the same `ResourceDictionary`**, not just present somewhere in it. First build attempt crashed on startup with `XamlParseException: Cannot find resource named 'BoolToVisibility'`. Fixed by moving all three converter declarations (`BoolToVisibility`/`InverseBoolToVisibility`/`EnumToBoolean`) to the very top of `Window.Resources`, before every `Style` that might reference them. **If a future `Style`'s `ControlTemplate` needs a converter via `StaticResource`, declare the converter before that `Style` in document order — this exact mistake is easy to repeat.**

**Not visually verified** — no screenshot capability here. Worth checking by hand: the overlay actually shows/hides at the right moments, and whether 6 seconds feels right for the shell-launch case (it's an unverified guess, not a measured value).

## Idle screen saver (2026-08-11)

New feature, not a fix. `Services/IdleDetector.cs` wraps `GetLastInputInfo` (user32.dll P/Invoke) for system-wide keyboard/mouse idle time — same mechanism Windows' own screen savers use, works regardless of which app has focus. It never sees gamepad input at all (XInput/`RawGameController` don't touch it), so `App.xaml.cs` separately tracks `_lastGamepadActivityUtc`, updated from `OnGamepadAction`/`OnRightStickMoved`/`OnRightTriggerChanged`. A 1s `DispatcherTimer` (`App.CheckIdle`) reloads `AppSettings` fresh **every tick** (deliberately not cached — it's a tiny JSON file, and this sidesteps needing any change-notification plumbing between the Settings UI, which edits its own `MainViewModel`-owned `AppSettings` instance, and `App`) and shows `ScreenSaverWindow` once both idle signals clear the configured duration, suppressed while `_runningGameProcess` is set, `_modalGamepadTarget` is set (some other dialog has gamepad focus), or it's already showing.

`ScreenSaverWindow` (project root, alongside `OverlayWindow`/`ArtworkCropWindow` — not `Views/`, since that's specifically for the four main screens): borderless/topmost/fullscreen/cursor-hidden. Two overlapping `Image` elements cross-dissolve (`Opacity` animated in opposite directions simultaneously, so z-order between them never matters) between a shuffled photo list every 12s, `DecodePixelWidth=1920` since source photos can be arbitrarily large. Music via `MediaPlayer` (`System.Windows.Media` — WPF's built-in MP3-capable player, no new dependency), shuffled looping playlist, ~1.25s fade in/out via a `DispatcherTimer` nudging `Volume` (WPF `MediaPlayer.Volume` isn't a `Storyboard`-animatable dependency property the normal way, hence the timer instead of a `DoubleAnimation`). Centered clock+date (`h:mm AM/PM` + `d MMMM, yyyy`, e.g. "11 August, 2026"), updated every second, plain white text with a `DropShadowEffect` rather than the app's own theme brushes — needs to stay legible over whatever photo happens to be showing, not just the app's usual dark surfaces. Dismissed by any keyboard/mouse/gamepad input — mouse move has an 8px jitter threshold so it doesn't self-dismiss the instant it appears; gamepad routing registers via the same `IGamepadInputTarget`/`SetModalGamepadTarget` pattern `ArtworkCropWindow` already uses.

Bundled assets: repo-root `assets/screenSaver/{images,sound}` copied into `src/CartridgeOS.Launcher/Assets/ScreenSaver/{Images,Sound}` (`Content`/`CopyToOutputDirectory` in the `.csproj`, same convention as `Assets/Sounds/*.wav`) — the repo-root copy is source material, not what the compiled app reads, same gotcha as the logo assets (see "Branding assets" above). `AppSettings.ScreenSaverImagesFolder`/`ScreenSaverMusicFolder` (both nullable) let a user point at their own folder instead — **replaces the bundled set entirely when set, doesn't merge** (explicit user decision after a shortcomings review) — `ScreenSaverWindow`'s constructor takes an `AppSettings` snapshot and resolves `settings.ScreenSaverImagesFolder ?? <bundled path>`.

**Settings tab** (`SettingsPanel.xaml`, new "Screen Saver" `TabItem`): enable/disable (`ScreenSaverEnabled`), inactivity-duration preset dropdown (`MainViewModel.InactivityOptions` — a static `IReadOnlyList<InactivityOption>`, 1/2/5/10/15/30 minutes, deliberately not a free-text field to avoid validating garbage input), a volume `Slider` (`ScreenSaverVolume`, 0–1), and Browse/"Use Default" button pairs for both folder overrides (`MainViewModel.BrowseForFolder` — a plain single-folder `OpenFolderDialog` wrapper, distinct from the scan-directory picker's MRU-list version since these are single overrides, not a recall list). "Preview Now" (`SettingsPanel.xaml.cs`'s `PreviewScreenSaver_Click` → `App.ShowScreenSaverNow()`) bypasses both the enabled toggle and the idle wait for testing, but still won't interrupt a running game.

## Tab-switch animations (2026-08-11)

**Main nav (Home/Recently Played/Library)**: `MainWindow.xaml`'s three screen hosts used to be gated by a straight `Visibility` binding (`EnumToVisibility`) — replaced with a per-screen `Style` (`HomeScreenFadeStyle`/`RecentlyPlayedScreenFadeStyle`/`LibraryScreenFadeStyle`) whose base state is `Opacity=0`/`IsHitTestVisible=False`, and a `DataTrigger` on `SelectedScreen` matching that specific screen animates `Opacity` 0→1 (0.25s `EnterActions`) / 1→0 (0.2s `ExitActions`). **These three styles must stay fully independent, not `BasedOn` each other** — a `BasedOn` relationship would carry over the base style's own `DataTrigger` too (`Style.Triggers` inherit, they don't get replaced by the derived style's triggers), meaning e.g. `RecentlyPlayedScreenFadeStyle` would *also* react to `SelectedScreen == Home` if it inherited from `HomeScreenFadeStyle` — caught this before it shipped, each style repeats the same base `Setter`s verbatim instead. All three screens stay technically "Visible" now (never `Collapsed`, since a collapsed element can't be animated) — tradeoff is the off-screen ones keep their own internal timers/animations running in the background (e.g. Recently Played's particle canvas), acceptable since it's opacity/transform-only GPU-composited work, not worth tearing down and rebuilding UserControls on every switch.

**Settings sidebar tabs**: `SettingsTabControlStyle`'s `ControlTemplate` originally tried an `EventTrigger RoutedEvent="Selector.SelectionChanged"` targeting the named `ScrollViewer` ("ContentHost") to fade the content area on every category switch. **Crashed on startup**: `Cannot find resource... 'ContentHost' name cannot be found in the name scope of ControlTemplate`. Root cause: `ComboBox` also derives from `Selector` and raises the exact same `Selector.SelectionChangedEvent` — the tab content has several (`ScanDirectories`, `StorageDrives`, `InactivityOptions`), and their own selection changes bubble up through the `TabControl`, triggering the `EventTrigger` in a context where it can't resolve `"ContentHost"` against the right template. **Any future `EventTrigger` on a bubbling routed event that a nested `Selector`-derived control could also raise needs the same caution** — fixed by moving to code-behind instead: `TabControl x:Name="CategoryTabControl" SelectionChanged="CategoryTabControl_SelectionChanged"` in `SettingsPanel.xaml`, and the handler filters `if (!ReferenceEquals(e.OriginalSource, CategoryTabControl)) return;` before reaching for `CategoryTabControl.Template.FindName("ContentHost", CategoryTabControl)` and animating its `Opacity` via `BeginAnimation`.

## Launch zoom-in animation (2026-08-11)

Per-screen artwork elements (Library's `GameTileStyle`, Home's `HomeCarouselItemTemplate`, Recently Played's hero card and `RecentRowStyle`) each gained their own dedicated `x:Name`d `Border` + `ScaleTransform`, distinct from any existing selection-scale transform on the outer tile (Library/Home already animate the *whole tile* on `IsSelected`) — a game can easily be both selected and launching simultaneously, and two `Trigger`s animating the same transform property on the same element would fight each other, so the launch-zoom targets a separate, artwork-only element instead. `DataTrigger Binding="{Binding IsLaunching}"` (or `ContinuePlayingGame.IsLaunching` for the hero, since that binds through a different root) scales 1.0→1.18 over 0.6s ease-out on `EnterActions`, back to 1.0 over 0.3s on `ExitActions`. `ClipToBounds="True"` added to each artwork element so the zoom doesn't spill past its own rounded corners into the tile's title/padding area.

## Playtime, screen-saver-suppression, and hero-highlight bugs (2026-08-11, all reported hands-on testing real non-seed apps)

Three related but distinct bugs surfaced in sequence while the user tested with real installed apps (Trello, Bandicam, etc.) rather than the seeded placeholder titles:

**(1) Playtime silently zero for short sessions**: `App.LaunchGame`'s `process.Exited` handler computed `int minutes = (int)(DateTime.UtcNow - startedAtUtc).TotalMinutes` (floors to the whole minute) and only called `RecordPlaytime` `if (minutes > 0)` — any session under 60 real seconds computed to exactly `0` and was dropped with no recording at all, which is exactly what a quick manual open/close test looks like. Fixed with a ceiling + 1-minute floor: `Math.Max(1, (int)Math.Ceiling(...))`, and the `> 0` guard removed since the result is now always ≥ 1.

**(2) Screen saver firing despite an app still being open**: a number of desktop apps — especially Electron/Squirrel-installed ones (Trello, Discord, Slack, VS Code all do this) — launch via a thin stub/updater `.exe` that spawns the real, longer-lived process and exits itself within a second or two. The tracked `Process.Exited` fired on that stub's exit, clearing `_runningGameProcess` back to `null` — the exact flag `CheckIdle` checks to suppress the screen saver — even though the real app window was still open and in active use. Fixed with a heuristic in the exit handler: before treating the exit as real, `Process.GetProcessesByName(Path.GetFileNameWithoutExtension(game.ExecutablePath))` — if any process sharing that exe name is still alive, treat this specific exit as the stub's, not the app's, and `return` before `RecordPlaytime`/`OnGameExited`. **Known, accepted limitation of this heuristic**: no attempt to re-attach tracking to the surviving process, so there's no second, accurate playtime/exit signal when the real app eventually closes on its own — `_runningGameProcess` is left pointing at the already-exited stub `Process` object (harmless for its only real use, a non-null check in `CheckIdle`/`ToggleOverlay`; `QuitRunningGame`'s `.Kill()` on it would throw, already caught, so no crash — it just wouldn't kill the real surviving process). Revisit with actual re-attachment/polling if this limitation turns out to matter in practice.

**(3) Newly-launched game not visually becoming the Recently Played hero**: turned out to be a selection-sync gap, not a `RebuildRecentGames` ordering bug (that part was already correct — verified by code inspection, not a guess). The hero card's highlighted state (`IsContinuePlayingGameSelected`) requires `SelectedGame == ContinuePlayingGame`; `RecordPlayed` moved the just-launched game into `ContinuePlayingGame` correctly, but nothing updated `SelectedGame` to match, so the hero showed the new game's title/artwork *unhighlighted* while whatever was previously selected kept its blue border in the 2x2 grid below — reading as "it didn't move to the hero card" even though its content had. `MainViewModel.RecordPlayed` now also sets `SelectedGame = game`.
