# Production Readiness

What's left before this ships to a real user's PC, beyond feature completion. Update as items are closed or new gaps are found.

## Current assessment (2026-08-17): not production-ready

Triage of the checklist below by actual severity, done when asked "if this goes to production is everything fine?" — not a new checklist, just prioritization of what's already tracked.

**Hard blockers (would actively hurt real users):**
- No physical controller has ever tested this app, despite it being marketed as controller-first — XInput/PlayStation mapping, right-stick mouse emulation, deadzones, the whole input layer is verified only by code inspection and self-checks. The single riskiest gap given the app's core pitch. See "Controller compatibility tested" under Testing.
- ~~No installer~~ — **fixed 2026-08-18**, see Packaging & install.
- No code signing — every launch will trigger Windows SmartScreen warnings, which reads as malware to most users. See Packaging & install.
- ~~No crash recovery~~ — **fixed 2026-08-18**: the installer now runs `sc failure` to set a real restart-on-crash policy as part of registering the Service, closing the one piece this was still waiting on. See Packaging & install.
- API keys (SteamGridDB, TheGamesDB) and the Discord Client ID are hardcoded into the shipped DLL — the Discord Client ID isn't actually sensitive (client IDs are meant to be public). The two bundled API keys are still shared by every install and can only be rotated by shipping a new build if abused — **narrowed 2026-08-17**: users can now opt into their own free key via Settings → Library → Artwork Sources instead of the bundled one, which removes the shared-key liability for anyone who cares to; the bundled key remains the default so nothing changes for anyone who doesn't. See Security below.

**Should-fix before calling it done:**
- Only Steam, Riot, EA, and the standalone/Xbox scanners have been checked against real installs (2026-08-16, Riot re-confirmed 2026-08-17 against a real VALORANT install on a non-system drive) — GOG, Ubisoft, Battle.net, and Epic are still unverified: none of the four are installed anywhere on this machine (checked registry + common install roots on C: and E:), so their 0-result runs only prove they fail closed safely, not that the publisher-keyword/exe-guessing heuristic (GOG/Ubisoft/Battle.net) or manifest parsing (Epic) picks correctly against real data. See Testing.
- ~~Named-pipe IPC has no message validation/sanitization yet~~ — **fixed 2026-08-17**, see Security.
- ~~No memory profiling on the long-running Service, no check that the artwork cache doesn't grow unbounded, no test with a large (500+) game library~~ — **fixed/measured 2026-08-17**, see Performance.
- ~~"Graceful handling of a game that fails to launch" isn't built~~ — **fixed 2026-08-17**, see Reliability.

**Lower risk / polish:**
- ~~No auto-update mechanism~~ — **fixed 2026-08-18**: nudge-only update-available banner (no silent auto-download). See Packaging & install.
- Several UI/animation details are marked "not visually verified" throughout progress.md/context.md — cosmetic risk, not functional risk, not re-listed here.

## Packaging & install
- [x] Installer (MSI/MSIX or Inno Setup) that registers the Service, installs Launcher, sets up autostart — **fixed 2026-08-18**: `installer/CartridgeOS.iss` (Inno Setup 6) + `installer/publish.ps1` (self-contained win-x64 publish of both `CartridgeOS.Launcher`/`CartridgeOS.Service` so end users never need the .NET runtime separately installed). Registers the Service with the SCM (`sc create`/`sc start`, `LocalSystem`, auto-start) and sets a restart-on-crash policy (`sc failure ... actions= restart/60000/restart/60000/restart/60000`) — the exact gap called out in the Reliability section's "no crash recovery" blocker, now closed. Launcher autostart uses an `HKLM\...\Run` registry value (opt-out checkbox, task default-checked), not a Startup-folder shortcut — see below for why. Verified with a real elevated install/uninstall cycle on this dev machine (not just a successful compile): service created and `Running`/`Automatic`, both exes present under `Program Files\Cartridge OS`, registry Run key present pointing at the right path, Start Menu shortcuts present — then uninstalled and re-verified all four are gone (`sc query` → service doesn't exist, install dir/registry key/Start Menu all absent).
- [x] Clean uninstall (removes service, registry entries, scheduled tasks) — **fixed 2026-08-18**, same installer: `[UninstallRun]` stops+deletes the service and kills a running Launcher process before file removal; the `uninsdeletevalue` flag on the Run registry value removes autostart automatically. Verified live (see above) — nothing survived uninstall.
- [ ] Code signing (avoid SmartScreen warnings) — still needs a real code-signing certificate (paid, identity-verified), out of scope for this environment to obtain.
- [x] Auto-update mechanism — **narrowed 2026-08-18**: per user request, built a nudge-only update check rather than silent auto-download/install (a full silent updater needs code signing first — see above — or every update triggers a SmartScreen/UAC prompt anyway, so it was explicitly scoped down). New `Services/UpdateChecker.cs` fetches `version.json` from this repo's GitHub raw URL on every launch (5s timeout, silent on any failure — offline/no-internet is not an error), compares against the running build's own `<Version>` (`CartridgeOS.Launcher.csproj`, kept in sync with the installer's `AppVersion` by hand), and if newer, `MainViewModel.ShowUpdateAvailable` shows a dismissible bottom-center banner with a "Download" button (opens the GitHub releases page via the same `Process.Start(UseShellExecute:true)` pattern used for the Settings hyperlinks). `version.json` lives at the repo root — bump it on release. Builds clean, all 10 self-checks pass. **Not visually verified** — a live UI check was in progress but stopped partway through when it became clear the user was actively using this machine's Visual Studio/browser at the same time, and continuing automated mouse/keyboard control risked interfering with their work; verified by code review only (the same `HasErrorMessage`/toast-banner pattern this reuses is already proven working elsewhere in the app).

**Real gap found and fixed during live testing (2026-08-18)**: the installer's `PrivilegesRequired=admin` combined with a `{userstartup}` Startup-folder shortcut for autostart is a genuine trap — `{userstartup}` resolves to whichever Windows account's token actually ran Setup, which on a real machine is not guaranteed to be the same account that'll actually use the app (confirmed live: installing from a separate elevated Administrator account put the shortcut in that account's own Startup folder, not the real end user's — Inno's own compiler even warns about this "UsedUserAreasWarning" pattern but doesn't block the build). Switched to an `HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\Run` registry value instead, which starts the Launcher at any user's logon on the machine regardless of which account performed the elevated install — verified this resolves correctly after the fix.

## Reliability
- [~] Service crash recovery / restart policy — **2026-08-17**: Service now calls `AddWindowsService()` (`Program.cs`) so it's SCM-controllable once installed; the actual restart-on-crash policy is an `sc failure CartridgeOS reset=...` call the installer still needs to make (no installer exists yet, see Packaging & install). Also added a global crash handler + append-only crash log (`%LocalAppData%\CartridgeOS\crash.log`) to the Launcher (`App.xaml.cs`) — previously zero diagnostic trail existed for any unhandled exception in either process.
- [x] Launcher crash doesn't take down the Service or leave the machine unusable — **checked 2026-08-17, not actually a gap**: separate OS processes (a Launcher crash can't touch the Service), and Windows' own crash dialog renders above topmost/fullscreen windows fine, so a crash doesn't strand the user without mouse/keyboard. No code needed here.
- [x] Graceful handling of games that fail to launch (missing exe, permissions) — **fixed 2026-08-17**: `App.LaunchGame` (`App.xaml.cs`) now distinguishes a real launch failure (Win32Exception/FileNotFoundException) from a legitimate Steam/Xbox shell launch (both previously returned `process is null`), clears the "Launching..." indicator immediately instead of minimizing the window, and surfaces the failure via the existing tray balloon tip instead of failing silently.
- [x] Named-pipe reconnect logic if Launcher starts before Service is ready — **checked 2026-08-17, not actually a gap**: `CartridgeOsPipeClient.SendAsync` already never throws (returns `null` on any connection failure), and nothing on the Launcher's real startup/runtime path depends on the Service's pipe — only the `--ipc-ping` diagnostic and cross-instance signaling do, both of which already handle a `null` response. No retry logic needed unless the Service becomes load-bearing for real functionality later.
- [x] Alt-tabbing (or otherwise activating another app, e.g. Chrome) away from the launcher didn't work — **found and fixed 2026-08-17, reported by user hands-on testing**: `MainWindow`'s `Topmost="True"` keeps it above every non-topmost window regardless of which one has actual keyboard focus, so switching to an ordinary app left that app rendering *behind* the still-fullscreen launcher with no visible way to reach it. `MainWindow.xaml.cs` now minimizes on `Deactivated`, guarded to only do so when the newly-foreground window belongs to a different process (`GetForegroundWindow`/`GetWindowThreadProcessId` P/Invoke) — otherwise the launcher's own child dialogs (PowerMenuWindow, ArtworkCropWindow, ScanResultsWindow) taking focus would incorrectly minimize it out from under themselves. Verified end-to-end with real window-activation testing (not just code inspection): restored the launcher to foreground/non-minimized, activated Notepad, confirmed the launcher minimized and Notepad became genuinely visible.

## Performance
- [x] Cold boot time to fullscreen UI measured and acceptable — **measured 2026-08-17** on this dev machine: ~4.1-4.3s from process start to the real fullscreen window appearing (distinguished from the splash window by checking `GetWindowRect` width > 1200px, since both share the same window title). Most of that is the splash screen's own deliberate choreography (`SplashWindow.xaml.cs`'s reveal animation, e.g. a 1100ms blur alone), not framework/data-loading overhead — see below, a 500-game library added only ~150ms on top of the ~4.15s baseline.
- [x] Game grid virtualization verified with large library (500+ games) — **verified 2026-08-17**: seeded a real 500-game library into `games.db` and cold-booted against it. Boot time barely moved (4147ms baseline → 4300ms with 500 games), working set landed at ~232MB, UI stayed responsive throughout (no hang) — consistent with `LibraryView.xaml`'s `VirtualizingPanel.IsVirtualizing="True"`/`VirtualizationMode="Recycling"`/`CanContentScroll="True"` + `VirtualizingWrapPanel` actually working, not just being configured. Also incidentally exercised the new artwork-fetch concurrency gate (below) under a real 500-item burst with no issues.
- [x] Artwork cache doesn't grow unbounded on disk — **fixed 2026-08-17**: previously nothing ever deleted a game's cached artwork when the game itself was removed, so repeated add/remove cycles (rescans, cleanup, re-adding under a different path) leaked cache files forever with no way to reclaim them short of nuking the whole `ArtworkCache` folder by hand. `ArtworkCache.PurgeCacheFor` (`Services/ArtworkCache.cs`) now deletes every decoded-size variant for a source path (globs by hash prefix, not a specific width, so it doesn't need updating if a new decode width is ever added) and `ArtworkFetcher.PurgeCache` (`Core/Scanning/ArtworkFetcher.cs`) deletes the downloaded boxart/hero originals — both called from `MainViewModel.RemoveGame`. Separately, also fixed an actual unbounded-*concurrency* bug found while looking at this: every caller fired artwork fetches fire-and-forget in a tight loop with no limit (startup load, post-scan import) — a 500-game library with no local artwork would have fired 500 concurrent HTTP requests at once. Added `ArtworkFetcher.ConcurrencyGate` (`SemaphoreSlim(4)`) around the network-bound portion of `FetchAndCacheAsync`; a full cache hit (the common case) never touches it.
- [x] Memory profiled for leaks in long-running Service (runs continuously) — **checked 2026-08-17** with real load, not just code inspection: ran the Service and fired 6000 sequential `Ping` requests at it in 3 bursts of 2000, watching `WorkingSet64`/handle count after each burst. Growth per burst: +32MB / +5.9MB / +7MB (19.8MB → 51.8MB → 57.7MB → 64.7MB), handle count nearly flat after the first burst (374 → 406 → 418). That decelerating-then-flat curve is the normal signature of .NET's generational GC warming up its heap segments, not a linear per-request leak (which would show roughly constant growth per burst). Scope caveat: the Service today only exposes `Ping`/`GetGameCount` — scanning/controller logic hasn't moved there yet (see context.md), so this doesn't cover the Service's *eventual* full workload, only what actually runs continuously today.

## Security
- [x] Named-pipe IPC validates/sanitizes messages — **fixed 2026-08-17**: `CartridgeOsPipeServer` (`Core/Ipc/CartridgeOsPipeServer.cs`) now (1) creates the pipe with an explicit ACL restricting access to Authenticated Users, so anonymous/guest logons on the same machine can no longer connect at all — previously the pipe had the OS default ACL, and this will matter more once the Service is actually installed and runs as LocalSystem; (2) rejects a request outright (before it ever reaches `handleRequest`) if `Command` is empty/whitespace/over 256 chars or `Payload` is over 4KB — sized to what every real command today actually needs (short fixed strings, no payload), not to `PipeFraming`'s 10MB framing-safety cap. Both processes' pipes go through this same server class, so Service and single-instance-signaling get the fix for free.
- [x] No arbitrary command execution beyond configured game launch paths — **checked 2026-08-17, already true**: the Service's command switch (`Worker.HandleRequest`) only exposes `Ping`/`GetGameCount`, and the only thing that ever calls `Process.Start` on IPC-adjacent code is game launching itself, which always reads `ExecutablePath` from the local SQLite DB, never from a pipe message.
- [x] SQLite DB not writable by untrusted processes — **fixed 2026-08-17**: `GameDatabase`'s constructor (`Core/Data/GameDatabase.cs`) now explicitly hardens the `%LocalAppData%\CartridgeOS` directory's ACL (protects it from inherited rules, grants only the current user + Administrators + SYSTEM) before opening the connection, rather than relying on whatever ACL the folder happened to inherit. Verified with `icacls` before/after: a pre-existing test folder that had inherited a broad sandbox-group grant lost that grant and kept only SYSTEM/Administrators/current-user after a real run. Since this directory is also where `settings.json`, the artwork cache, and every `*.log` file live, they get the same hardening for free (inherited from the now-protected parent) — this was the one call site guaranteed to run first in both the Launcher and Service startup paths. Best-effort/non-fatal if it can't set the ACL (e.g. non-NTFS volume); a pre-existing `games.db` file itself keeps its old file-level ACL until rewritten, only the directory (and anything created in it afterward) is affected.
- [x] Hardcoded API keys — **narrowed 2026-08-17**: `ArtworkFetcher.cs`'s bundled `SteamGridDbApiKey`/`TheGamesDbApiKey` are still shared by every install (rotating either still means shipping a new build — an env var would buy no real protection for a closed-source app, see the file's own comment), but a user who cares can now opt out of the shared key entirely via Settings → Library → Artwork Sources, pasting their own free key instead. `AppSettings.SteamGridDbApiKeyOverride`/`TheGamesDbApiKeyOverride` (blank = use the bundled key); `ArtworkFetcher.EffectiveSteamGridDbApiKey`/`EffectiveTheGamesDbApiKey` resolve which one to use per fetch. The Discord Client ID needed no change — client IDs are meant to be public, not a real secret.

## UX / accessibility
- [x] Full controller-only navigation with no dead ends (every screen reachable/exitable via controller) — the header's old bare Minimize/Close buttons were replaced with a Power button/menu (Exit to Desktop / Shut Down Cartridge OS / Restart System / Turn Off System), bound to the controller Start button (`GamepadAction.Power`) and keyboard F4, fully controller-navigable
- [x] Keyboard/mouse fallback still works for setup/debugging — **fixed 2026-08-18**: live-tested keyboard-only (no controller attached), driving the real running app via simulated input and screenshots rather than just code inspection. Found and fixed a real bug: `MainWindow`'s window-level `PreviewKeyDown` (tunneling) intercepted Left/Right/Up/Down/Enter/Escape *before* a focused `TextBox` ever saw them, so typing in the Settings API-key fields or the Library search box couldn't move the text cursor, and Escape/Enter didn't do normal text-field things either — reproduced live (typing "abcdef", pressing Left×3, typing "XYZ" produced "abcdefXYZ" instead of "abcXYZdef") and confirmed fixed with the same test after the change (`MainWindow.xaml.cs` now skips the handler entirely when `Keyboard.FocusedElement is TextBox`, letting the TextBox handle its own keys natively). Also found `OverlayWindow` (the in-game overlay) was the one modal dialog with no keyboard equivalent at all, despite `keybinds.md` documenting keyboard parity for every `GamepadAction` — mouse always worked there since it's a normal WPF window with clickable buttons, but added the same `PreviewKeyDown` pattern already used by `MainWindow`/`PowerMenuWindow` for consistency. Verified globally-bound keys (Tab→Settings, arrow nav, Enter→Confirm, Escape→Back, F4→Power) all work via keyboard alone outside of TextBoxes. All 10 automated self-checks (`dotnet test`) pass after the fix.
- [x] Error states are visible in fullscreen mode (no silent failures) — **fixed 2026-08-17**: audited every catch-adjacent path in `MainViewModel`/scanners and found the real gap — `ScanForGames`/`ScanTrustedLauncherSources` (and the Find More Games heuristic scanners) had *zero* exception handling around any individual scanner, so a single scanner throwing (malformed registry data, an unreadable install folder, a bad manifest) propagated all the way to `App`'s `DispatcherUnhandledException` and crashed the entire fullscreen session over what should be "one scan source didn't work" — the fullscreen kiosk shell has no title bar/status bar for that to show up in otherwise, so it was either fully silent or (worse) took the whole app down. Fixed by isolating each scanner in its own try/catch (one failing no longer stops the others or the app), added a new on-screen error toast (`MainViewModel.ShowError`/`ErrorMessage`/`HasErrorMessage`, rendered top-center in `MainWindow.xaml`, auto-dismisses after 6s or via a close button) surfaced on every user-initiated scan failure, and a `scan.log` (same append-only pattern as `crash.log`/`discord.log`/`artwork.log`) for diagnostics — the periodic 15-minute background rescan logs failures but deliberately doesn't toast, so a scanner that's reliably broken on one machine doesn't pop an unprompted error forever. Also wrapped the DB-write paths that had the same gap (`AddGame`, `RemoveGame`, `ChangeArtwork`, `RevertArtwork`, `ChooseWallpaperAsync` — any of `_db.*`/`SettingsStore.Save`/file I/O throwing previously had the same "crash the whole app" failure mode) to show the same toast instead. Builds clean, all 10 self-checks pass, smoke-tested live (launched the real exe, no crash.log entry). **Not yet forced to actually trigger** — none of these exceptions have been reproduced on a real machine (no scanner has actually thrown here), so this is verified by code inspection + a clean normal run, not by watching a real failure get caught.

## Testing
- [ ] Scanner tested against real installs of each supported launcher — **partially done 2026-08-16, re-checked 2026-08-17**: Steam, Riot, EA, standalone-executable, and Xbox scanners verified against real installs on one dev machine (see progress.md/context.md 2026-08-16 entries) and several real bugs found+fixed there (Riot title bug, missed/mistitled nested installs, Xbox false-positive flood, Steam duplicate). 2026-08-17: re-ran `RiotScanner.Scan()` directly against a real VALORANT install on E: — correctly resolved title "VALORANT" (climbing past the "live" wrapper folder) and the Riot Client exe path. Epic, GOG, Ubisoft, and Battle.net still unverified — confirmed none of the four are installed anywhere on this machine (checked HKLM/HKCU uninstall registry + common install roots on both C: and E:), so there's no real data to test the publisher-keyword/exe-guessing heuristic (GOG/Ubisoft/Battle.net) or manifest parser (Epic) against.
- [ ] Controller compatibility tested: Xbox, DS4, generic HID/DirectInput — **the single riskiest open item in this whole file, now partially informed by real testing**: 2026-08-17, user hands-on tested with a real Xbox controller and found the button mapping confusing/broken-feeling — the Guide/Xbox button (carrying both "open item options" and overlay-toggle) often didn't seem to do anything, root-caused to Windows' own Xbox Game Bar globally intercepting that exact button by default (Settings → Gaming → Xbox Game Bar), which this app cannot suppress. Fixed by moving "open item options" to the Start/Menu button (matches real Xbox Home/PS5 dashboard convention) and keeping Guide's role but no longer as the sole path to anything essential — see `keybinds.md`'s 2026-08-17 log entry for the full before/after. **This fix itself is not yet re-verified with the real controller** — still needs a hands-on retest. Beyond this specific finding, DS4/PlayStation and generic HID/DirectInput controllers, right-stick mouse emulation feel, and deadzone tuning remain untested with real hardware — everything there is still verified only by code inspection, self-checks, and the not-connected code path not throwing.
- [x] Multi-monitor behavior verified — **fixed 2026-08-18** on this dev machine's real two-monitor setup (found via a live test that this was actually broken, not just unverified): the screen saver (`App.ShowScreenSaver`) previously only ever covered the primary monitor, leaving every other monitor fully visible/interactive — confirmed live (screenshotted both monitors, secondary monitor still showed the desktop underneath). Fixed: the slideshow/clock/music (`ScreenSaverWindow`) still only plays on the primary monitor (unchanged), but every other monitor now gets a new `ScreenSaverBlankWindow` — a plain black fullscreen window, same idea as how Windows' own lock screen only shows its full UI on one monitor and blacks out the rest. Dismissing any one of them (input on either monitor, or gamepad) closes all of them together (`Dismissed` event on both window types, wired through `App`). New shared `Input/MonitorHelper.cs` (P/Invoke `EnumDisplayMonitors`/`GetMonitorInfo`/`SetWindowPos`) positions windows in physical pixels rather than WPF's DIP `Left`/`Top`, sidestepping per-monitor DPI conversion entirely. Also fixed two related real gaps found while working on this: (1) `MouseEmulator`'s right-stick mouse emulation clamped cursor movement to the primary monitor's bounds only (`GetSystemMetrics(SM_CXSCREEN/SM_CYSCREEN)`) — the cursor could never be moved onto a second monitor at all; now uses the virtual-desktop bounds (`SM_XVIRTUALSCREEN`/etc.) instead, this was already a known/flagged gap (see progress.md 2026-08-17) with the exact fix pre-identified. (2) the in-game overlay (`OverlayWindow`) was hardcoded to `SystemParameters.WorkArea` (always the primary monitor's work area) — on a setup where the game runs on a secondary monitor, the overlay would've popped up on the wrong monitor entirely; now targets whichever monitor the foreground window (the running game) is actually on via `MonitorHelper.GetMonitorBounds`. Verified live end-to-end for the screen saver (real two-monitor screenshots before/during/after dismiss); the overlay fix is verified by code review + reuse of the same already-tested `MonitorHelper` primitives, not a live test with an actual running game on a secondary monitor (couldn't set that up in this environment). Builds clean, all 10 self-checks pass (one transient failure during testing was traced to this session's own screenshot/cursor automation racing the self-check, not a regression — reran in isolation and it passed).
- [x] Self-checks are automated, not just manually-invoked CLI flags — **fixed 2026-08-17**: new `src/CartridgeOS.Tests` xUnit project (`dotnet test`) wraps all 10 `--self-check-*` modules as `[Fact]`s (`SelfCheckTests.cs`), so they run together as a pass/fail suite discoverable by CI instead of requiring someone to remember and run each flag by hand. The `--self-check-*` flags themselves are untouched (same `Run()` methods) and still work standalone.
