| 2026-08-07 | Evaluated Suspend/Resume (next Phase 3 item) and decided **not to build it**, per user instruction after explaining the tradeoff — recording the full reasoning here rather than just the checklist line. **What it would actually be**: unlike a console (which snapshots a game's full RAM/GPU state to disk so it can fully close and resume instantly later), Windows has no OS-level equivalent for suspending an arbitrary desktop process. The only thing technically achievable is *freezing the process's threads* via the undocumented `NtSuspendProcess`/`NtResumeProcess` NTAPI functions — the same mechanism Process Explorer's "Suspend" button uses. That stops CPU usage while frozen but does **not** release GPU/VRAM, does **not** serialize any state, and the process resumes exactly where its threads left off (not equivalent to a real pause of game logic/timers either — a frozen game with a live network socket just stops responding rather than "pausing" gracefully). **Why it's risky, not just unpolished**: anti-cheat software (EAC, BattlEye, VAC) actively watches for externally frozen threads as a tampering signal — suspending a process running one of these can trigger a ban, and this covers most competitive/online games, not a rare edge case. It's also built on an undocumented API with no Microsoft stability guarantee across Windows versions. The realistic benefit (freeing CPU momentarily for single-player, non-anti-cheat games) is a narrower slice of the actual game library than "Suspend/Resume" as a checklist item implies. Given this is meaningfully riskier than anything else shipped so far (nothing else here can get a user's game account banned), it needs a much stronger case before it's worth building — revisit only if there's a specific, safer use case (e.g. scoped to a user-maintained allowlist of known-safe single-player titles) rather than a blanket feature. |
